#### 10.13.269 Постановка: родительское Value как навигатор (`Parent is Navigator`) — **сделано в цикле 92** (10.13.271)

**Его заказ** (заметка тестов, 2026-09-24): «сделать опцию, чтобы родительское value было не значением, а навигатором, т.е. только обрезало значения sub-field». Пример — Field `Clients` типа Link: родитель `AK` с детьми `[[клиент1]]`, `[[клиент2]]`, родитель `IEDT` с детьми `[[клиент3]]`, `[[клиент4]]`. Выбрал в tagWheel `AK` — в дочернем Field только его дети; родителя не выбрал (например, через `Alt`) — все четыре. После `Enter` на строке только дочернее Value, навигатора на строке нет: «это виртуальное value, нужно только для выбора». То же для Field типа Tag. Его способ — контрол `Parent is Navigator` под `Child Field`, недоступный при `Hide`; при `On` родительские Values не пишутся на строку и не вызываются `next`/`previous`.

**Что уже есть и на что постановка опирается.**

- дочерний Field — это отдельный Field `<имя>_sub` со своими Values; у каждого Value список `allowedParentValues`, у родительского — `subtags`. Отбор детей по родителю — `getAllowedSubValues` (`tagwheel_core.js`), принадлежность «какому родителю этот ребёнок» — `parentValueIdForChildValue` (`pkm_rules_runtime_helpers.js`), одно объявление на обе дороги (10.13.215);
- `Child Field` = `Always` + `Parent Value` = `Child only` уже даёт половину: команды дочернего Field листают **все** его Values, и родитель на строку не дописывается (10.13.215, 10.13.216). Навигатор добавляет к этому три вещи: родителя **нельзя записать** и выбором в tagWheel, и командой; выбор родителя в tagWheel **только сужает** список детей; открытая на строке с ребёнком панель **сама ставит** родителя по ребёнку;
- `On Alt` без значения у родителя уже показывает всех детей (`В-195`, 10.13.251) — ровно его «не выбрав parent — увидел бы все».

**Нюансы, которые его формулировка не закрывает.**

1. **У Field типа Link дочернего Field сегодня нет вовсе** — ни в панели (ряд `Child Field` рисуется только у Tag), ни в движке (ключи `_sub` и отбор по родителю живут в движке тегов, `status_tags.js`). Привязка ссылки к родителю (`__ioParentBinding`) осталась только в модели панели, движок её не читает (фаза 3b). Значит, его главный пример — `Clients` — требует сначала **дочернего Field для Link**: ряд в редакторе, колонку родителя у Values ссылки, круг `next`/`previous` по ссылкам с отбором, запись wikilink. Это отдельная работа, крупнее самого навигатора. Вопрос 1 интервью.
2. **Имя навигатора у ссылки — не ссылка.** `AK` — подпись группы, а не заметка. Редактор Values ссылки сегодня требует форму wikilink (`A link needs a name`); у навигатора должна быть простая подпись, и заметка по ней не создаётся. У тега навигатор может остаться тегом (`#AK`) — на строку он всё равно не попадает.
3. **Формат дочернего тега `Nested` (`#doing/review`).** При нём родитель — часть написания ребёнка. «Родителя нет на строке» тогда значит либо писать `#review`, либо оставить `#doing/review` как единое написание. Вопрос 2 интервью.
4. **`next`/`previous` дочернего Field на строке, где ребёнок уже стоит.** Листать всех детей подряд (как `Always` сейчас: `[[клиент1]]` → … → `[[клиент4]]`) или только детей того же навигатора (`[[клиент1]]` ↔ `[[клиент2]]`), раз навигатор выводится из ребёнка. Вопрос 3 интервью.
5. **Команды самого родительского Field.** Если все его Values — навигаторы, `next`/`previous` писать нечего. Моё умолчание: Values родителя без детей остаются обычными и листаются, навигаторы команда пропускает; если обычных нет — команда говорит `Notice` «нечего листать» (тихий отказ запрещён, У-41), а не молчит. Прятать команды из палитры не предлагаю: набор команд строится при загрузке, и у Field, правленного в панели, шва пересборки нет (У-79).
6. **Что навигатор, а что нет.** «Все родительские value» читаю как «родительские Values, у которых есть дети». Value родителя без детей — обычное Value и пишется как прежде. Иначе Field, где часть значений — группы, а часть — самостоятельные, потерял бы самостоятельные.
7. **Ребёнок принадлежит двум навигаторам.** `allowedParentValues` — список, ребёнок бывает общим. Выводя навигатор по ребёнку для открытой панели, беру **первого** по порядку Values родителя; в сужении ребёнок виден под каждым своим навигатором.
8. **Режимы `Child Field` при навигаторе.** `Hide` — контрол недоступен (его слово). `After parent` — «после выбора навигатора в tagWheel»; предусловие команд «родитель на строке» при навигаторе снимается: родителя на строке не бывает никогда, иначе дочерний Field стал бы недостижим командами. `Always` — дети видны сразу, выбор навигатора сужает. `On Alt` — как сейчас. Ряд `Parent Value` (`Child only` / `Add parent Value`) при навигаторе прячется: запись родителя навигатор запрещает по определению.
9. **Родитель, уже записанный на строках.** Включённый навигатор не решает судьбу написанного (правило 107): `#AK`, стоящий на старых строках, остаётся, пока человек его не снимет. Панель на такой строке ставит навигатор по нему, а не по ребёнку.
10. **Кто ещё спрашивает родителя.** `Prerequisite Field`, ждущий родительского Field, при навигаторе ждал бы вечно; моё умолчание — такое ожидание отвечает выведенным из ребёнка навигатором. `Smart Rules` с условием на навигатор (`when the line has AK`) — то же: линия «имеет AK», когда на ней ребёнок `AK`. YAML (`Inline to note`) — свойство родительского Field получает выведенный навигатор (`Clients group: AK`); это даёт группу в свойствах заметки без записи на строку. `Prefix` по значению, цвета и `Bars` у навигатора не действуют — рисовать на строке нечего.

**Где ляжет правка** (адреса, не число мест — считать буду до кода, правило 172). Конфиг: карта `subNavigator` рядом с `subOnAlt` и перенос на определение поля (`parentIsNavigator`) через все перечни дороги — `parseOrderConfig`, `normalizePkmOrder`, `normalizeField`, подделки нормализатора (правило 159). Панель: ряд в прототипе и `fields_editor_view.ts`, тексты в `texts_blocks.ts`. Движки под З3 (`tagwheel_core.js`, `tagwheel.js`, `status_tags.js`, `pkm_rules_runtime_helpers.js`) — по `В-162` как назначенная им работа: полный разбор, измерение, правка, мутация. Мера — новая половина обхода `tools/line_matrix.js`: навигатор не появляется на строке ни одной дорогой, круг детей замыкается, панель встаёт на навигатор ребёнка.

**Порядок, который предлагаю.** Сперва навигатор для Tag — механика дочернего Field там уже есть; затем дочерний Field для Link и навигатор на нём. Оба шага — своими тестами в заметке.

**Его ответы тем же заходом.** `В-218`: сперва Tag, потом Link. `В-219`: при `Nested` на строку пишется только ребёнок (`#review`). `В-220`: `next`/`previous` дочернего Field листают **всех** детей подряд, как `Always` сейчас, — навигатор сужает только список в tagWheel, команды его не спрашивают. Нюанс 4 закрыт этим ответом; остальные умолчания (5–10) стоят, пока он не скажет иного.

#### 10.13.264 Висячий отступ вернулся: 28 против 54 (2026-09-24, ночь) — без правки

**Его данные к тесту 2.** Строка второго уровня (`\t- `) с дефектом: `text-indent: -28px; padding-inline-start: 28px`; после выключения плагина — `-54px`/`54px`; включение обратно дефекта не вернуло; позже дефект вернулся сам, после прокрутки ниже и набора там. В этой длинной заметке он чаще.

**Версия 10.13.259 этот случай не объясняет.** Там разница 22 − 10 = 12 была полем `0.75em` у знака списка в Live Preview. Здесь разница 26, а замер в Source mode дал бы 54 − 12 = 42, не 28.

**Что выключение плагина значит на самом деле** (прочитано в `app.js` 1.13.7). Выключение и включение снимают и ставят `styles.css` плагина; загрузка стилей зовёт `workspace.trigger("css-change")`, а каждый редактор отвечает на него `onCssChange` → `dispatch({effects: clearCache.of()})` и `editor.refresh()`. `clearCache` стирает весь `indentCache` — и строка перемеряется. То есть «выключил — прошло, включил — не вернулось» — это сброс кэша Obsidian, и отличить им дефект плагина от дефекта Obsidian нельзя.

**Где кэш может отдать чужую ширину** (там же, `buildDeco` и `getCached`). Кэш хранится по **номеру** строки и на правку документа не сдвигается. При промахе он берёт запись соседней строки с тем же началом, а если и её нет — **любую запись этой строки по номеру с началом той же длины** (`i.text.length === t.length`). Начало ищется регуляркой `^([>\s]*)(([*+-] |(\d+)([.)] ))(?:\[(.)\] )?)?`: у `\t- ` длина 3, как у `1. `. Перемеряется строка, только если наблюдатель DOM пометил её изменённой или текст начала не совпал; строка вне экрана не перемеряется вовсе. Это совпадает с его наблюдением «в этой заметке, где много текста, чаще»: больше строк — больше сдвигов номеров. Но какой именно ход дал 28, чтением не выводится.

**Мой обмер не сошёлся с его экраном**, и выводов из него нет: его строка из `outerHTML` на странице с `app.css` 1.13.7, темой Minimal и нашим `styles.css` дала 22 точки там, где у него 54 (табуляция на моей странице ширины не прибавила) — страница не повторяет его редактор. Третья догадка запрещена (У-70).

**Кода плагина это не касается ни строкой**: наших правил отступа строки и слушателей `css-change` в `src` нет (греп `text-indent`, `padding-inline-start`, `HyperMD-list`, `cm-indent`, `css-change`). Тест 2 переписан на шаг, который различает двух подозреваемых: сброс кэша **без** плагина — переключение светлой и тёмной темы, оно тоже зовёт `css-change`, — и работа в этой заметке с выключенным плагином.

#### 10.13.261 Scroller приклеен к панели, а не к экрану (2026-09-24, ночь)

**Его замечание:** «баг — при открытии tagwheel при включенном scroller — если проскроллить экран, то scroller следует за экраном, а должен быть приклеен к панели tagwheel».

**Причина.** Коробка скроллера стоит `position: fixed` на `document.body` и ставится по координатам якоря на каждое обновление панели. Прокрутка заметки обновлением панели не была: якорь уезжал вместе со строкой, коробка оставалась на месте экрана.

**Правка** — `src/ui/tagwheel_scroller_overlay.js`, файл не под З3. Оверлей запоминает последний вызов и слушает `scroll` у прокручиваемого узла заметки (`cm.scrollDOM`); прокрутка ставит коробку заново тем же `update` не чаще раза за кадр. Якорь, ушедший за край области заметки, коробку прячет: прижим к краю окна иначе оставлял бы её висеть у края экрана. `hide()` панели забывает последний вызов — спрятанное панелью прокрутка не возвращает. Слушатель на `document` запрещён правилом каталога (`catalog_rules_tests.ts`, «слушатель на document мимо registerDomEvent») — первая версия правки его и нарушила, сторож покраснел.

**Чем закреплено.** `tagwheel_scroller_overlay_tests.js`: коробка стоит под якорем; без события не двигается (контроль шага); после прокрутки переехала вместе с якорем; якорь вне области — коробки нет, вернулся — вернулась; `hide` прокрутка не отменяет; после `destroy` слушателя нет. Подмены «не слушать», «не прятать вне области», «hide не забывает» краснеют каждая на своём утверждении; подмена «слушатель заводится повторно» зелена законно — снятие и постановка оставляют его одним (правило 144).

#### 10.13.260 Custom block: свой tagWheel у курсора (2026-09-23, ночь; поправлено 2026-09-24) — **сделано 2026-09-24, ночь**, ждёт его проверки (тесты 2–5)

Он попросил «уточни детали и сформулируй грамотную постановку»; развилки решены интервью `В-203`…`В-206`. Описание по Р13 — до кода.

**Правка 2026-09-24 — его `💬` к тесту 1.** Первая редакция говорила: «пар `next`/`previous` у Field из custom block нет». Его слово: «это неверно. Пары должны создаваться, `next`/`previous` также должны работать, но с условием — что работают они только, когда курсор находится на этом value». Отсюда же уточнение `В-204`: панель по-прежнему открывается пустой, **кроме** случая, когда каретка стоит на значении Field этого блока. Плюс четыре новых пункта: переключение custom block по `Tab` новым контролом, новый раздел настроек `tagWheel behavior` на `Tags & PKM`, поддержка custom block тремя переезжающими туда контролами и панель, которая разрывает текст на месте каретки. Ниже всё это вписано на свои места; развилки, которые из его слов не следовали, — `В-207`…`В-209`, отвечены интервью тем же заходом.

**Почему Free ломает Block (разбор кода, 2026-09-23).** `applyFullTagNormalization` (`tagwheel.js`) на **каждом** `Enter` снимает со строки и ставит заново к курсору, запомненному при открытии, все Free-значения строки, а не только те, что крутили. Free к тому же работает только у тегов Left Block: при `panel === 'right'` режим сбрасывается в `off` (`collectSelectedTagEntries`, `relocateTagLikeByOrder`). Открывать панель у курсора движок не умеет: полоса встаёт в зону своего Block (`renderControlLine`), сторона везде двоичная (`getMode`, `buildPanelGroupsFromTechOrder`, `resolveStartMode`), Tab переключает `left` ↔ `right`.

**Что человек видит в панели настроек** (`Tags & PKM` → `Fields`, список `io-fields-list`):

1. Под Right Block — по разделу на каждый custom block в порядке создания; у подписи раздела карандаш (переименовать) и корзина (удалить). Карандаш зовёт то же окно, что карандаш у Field (`askRenameModal`).
2. Рядом с `Add Field` — кнопка `Add Block`, **не акцентная** (`io-btn` без `io-btn--cta`): его слово «цвет кнопки должен отличаться от add field». Создаёт пустой блок с именем `Custom block N` — первым свободным N.
3. Field переносится в custom block и обратно теми же средствами, что между Left и Right: перетаскивание на раздел, на подпись, на строку, и стрелки. Стрелка на краю раздела уводит в соседний раздел сверху вниз: Left → Right → custom 1 → … Дочерний Field ходит за родителем, как сейчас.
4. **Один Field — один блок.** Перетаскивание переносит, а не копирует.
5. **Типы Field — любые** (`В-206`): тег, ссылка, дата, элемент.
6. `Behavior` у Field в custom block **не показывается**: там он всегда Free, а контрол без выбора — З8. У Field в Left/Right в `Behavior` остаются `Strict` и `Insert only`, `Free` снят.
7. **Имя блока** — непустое, без повторов среди блоков; пустое переименование не пишется, повтор отказывает той же ошибкой, что у имени Field (`ERR_NAME_TAKEN`).
8. **Удаление — вместе с Field** (`В-205`). Если в блоке есть Field, открывается окно подтверждения, в котором названо их число и имена: «Delete block X and its N Fields?». У пустого блока окна нет. Field снимаются тем же путём, что `deleteField` (Order, оба списка по типу, дочерний вместе с родителем). Хоткей, назначенный на команду блока, остаётся в `hotkeys.json` мёртвым — так Obsidian ведёт себя с любой снятой командой.

**Команда.** У каждого блока одна команда: имя `tagWheel <имя блока>`, идентификатор `open-tagwheel-custom-<id>`, где `id` выдаётся при создании и больше не меняется. Переименование меняет имя, а не идентификатор, поэтому хоткей переживает переименование. Заводится при создании блока, снимается при удалении (`Plugin.removeCommand`, есть с 1.7.2; `minAppVersion` у нас 1.13.0), при переименовании перезаводится с тем же идентификатором. Хоткея по умолчанию нет (З7). Справочник команд (`buildOwnCommandList`) показывает и их — комментарий «tagWheel всегда ровно две» снимается.

**Пары `next`/`previous` у Field из custom block заводятся** (правка 2026-09-24), тем же `buildPkmCommandDefs` и с тем же идентификатором от ключа Field, что у Left/Right: перенос Field между блоками хоткей не теряет. Работают они **по месту каретки**, а не по строке:

- **Каретка на значении этого Field** — `next`/`previous` меняют **это** значение на соседнее в списке Field, остальные копии в строке не трогают. «На значении» — его словами «каретка стоит в тексте value, сразу после него, либо до него»: `|aaa`, `aa|a`, `aaa|`. Значение узнаётся по написанию одного из Values этого Field целиком, с границей слова с обеих сторон, — то есть тем же вопросом, которым его узнаёт разбор строки, а не своим (правило 72).
- **Каретка не на значении** — «это воспринимается как отсутствие значения»: `next` вставляет у каретки первое значение Field, `previous` — последнее, новой копией и по правилам пробелов из пункта 4 ниже. Ни одна из уже стоящих копий не меняется.
- **Цена, названная вслух:** набранное руками слово, совпавшее по написанию с Value, тоже считается значением — и команда, и панель на нём поменяют именно его. Это следует из «распознавать введенное значение как value»; у Left/Right то же самое, только их зона — края строки, а у custom block зона — вся строка.

**Что происходит в строке:**

1. Команда блока открывает панель **у курсора**: полоса встаёт в текст на месте каретки, а не в зону Left/Right. Если есть выделение — на его конце, выделенный текст не трогается.
2. **Текст строки панель не прячет, а разрывается на месте каретки** (его пункт от 2026-09-24): `каретка курсора | продолжение текста` → `каретка курсора ==**[Field1]** `Field2`== продолжение текста`. Левее и правее полосы остаётся всё, что было; прячется только то, что прячет `Values in the other Block` (пункт 9).
3. В панели только Field этого блока. Вид, прокрутка, клавиши, `Alt` и дочерние поля — те же, что у Left/Right, и управляются теми же контролами (`visual.tagWheel`).
4. **Панель открывается пустой — если каретка не на значении.** Его пример: выбрал `ааа`, печатает дальше, снова зовёт панель — она пустая, и второй `ааа` встаёт новой копией; потом `ббб` прокруткой — третья вставка. «Ни одно из ранее введенных value не должно удалиться. Каждый вызов tagwheel custom открывается пустым».
5. **Каретка на значении Field этого блока** — панель открывается на этом Field и показывает стоящее значение выбранным: «если я выбрал value и затем повторно активирую tagwheel custom, то тогда панель должна показывать выбранное значение». Условие «на значении» — то же, что у `next`/`previous` выше. `Enter` **заменяет стоящее значение на месте** (`В-207`, его ответ «заменить на месте»): другие копии не трогаются, значения остальных Field блока, выбранные в этой панели, встают сразу за ним.
6. `Enter`: выбранные значения всех Field блока идут в порядке Field блока через пробел и встают у курсора. Пробел ставится до вставки, если перед ней не пробел и не начало строки, и после, если за ней не пробел и не конец строки. **Больше в строке не меняется ничего**: ни Prefix, ни буллит, ни порядок Left/Right. Каретка встаёт за вставкой. Значение пишется тем же текстом, что Field пишет в своём Block: дата — в своём формате, ссылка — в своей форме, элемент — своим знаком.
7. `Esc` — ничего не записано.
8. **`Tab` решает новый контрол `tagWheel - Switch custom blocks on Tab`** (правка 2026-09-24). Выключен — `Tab` ничего не делает, как в первой редакции: его прежнее слово «нажатие tab должно переместить left\right panel, но никак не взаимодействовать с tagwheel custom panel» остаётся в силе для панели Left/Right — её `Tab` в custom block не уводит ни при каком положении контрола. Дополнение к исключению З3 № 148.

**Чем закреплено.** Браузерный шаг: `Alt`, `←`, `→` настоящими событиями окна, с контролями «открылось», «ушёл» и «вернулся»; подмена «сброса нет» краснеет его сценарием. Прежнее утверждение «держится после следующей клавиши» шло `→` на чужое поле — то, что он теперь запретил; следующая клавиша в нём — `↑`, с поля не уводящая.

Три мутации, каждая краснеет на своём утверждении. В браузерном шаге — четыре состояния гиперссылки на **своей** паре значений (все четыре цвета страницы разные, У-147) и утверждение «гиперссылка не взяла цвет wikilink»; подмена `ext-link-shares-wikilink` возвращает прежний код и роняет именно его (У-223).

#### 10.13.243 Перенос текста пишет окно строки, а не весь документ (2026-09-22)

**Его слова:** «при переносе выделенного текста move left\right прыгает экран — так быть не должно. Он должен оставаться где и был».

Первой схлопывается свёртка: свёрнутый кусок выше рабочей строки разворачивался от одного нажатия, заметка вырастала, и экран уезжал на его высоту.

**Числа.** Прежняя запись: свёрток 1 → 0, прокрутка 1006 → 2840 на первом же нажатии, дальше стоит (разворачивать больше нечего). Нынешняя: свёрток 1 → 1, прокрутка 1006 на всех четырёх нажатиях. Заметка без свёрток — граница правки: там обе записи держат экран, и стенд на этом падает, если вдруг уехал (У-164).

**Правка — один помощник на все четыре места.** `writeMovedWindow(editor, doc, from, to, insert)` зовёт `replaceRange` по окну изменившегося куска строки; окно никогда не шире строки, потому что стену ставит `moveTextBounds`. Текст не меняется ни на знак: окно собрано из тех же кусков, из которых прежде собирался весь документ, и условие «писать, только если стало другим» переведено буквально — `doc.slice(from, to) === insert`.

**Чем закреплено — двумя сторожами разного рода.** Первый: `node tools/move_scroll_bench.js` с настоящим `EditorView`, обёрткой `Editor`, списанной с `app.js` 1.13.7, заметкой в двести строк и свёрнутым куском выше рабочей строки. Контролей четыре, каждый на свой шаг (правило 64): возврат прежнего кода `--legacy`, заметка без свёрток как граница, нажатие в стену и требование, чтобы странице было куда ехать. Второй: подделка редактора в `navigation_jumps_tests.js` на `setValue` **громко отказывает** — любая новая дорога переноса, написанная заменой документа, роняет прогон там же, где её завели. Проверено возвратом прежнего кода: прогон краснеет именно на этом утверждении.

**Цена.** Окно пишется без `userEvent`, значит фильтр нумерации Obsidian теперь видит и правку переноса текста — как видит правку от рук человека. `node tools/renumber_bench.js` зелёный на всех двенадцати случаях; обход строки `node tools/line_matrix.js` — те же 10 из 162, что и до правки.

#### 10.13.239 Перенос выделенного не втыкается в оформление строки (его замечание к тесту 9) (2026-09-22)

**Его слова:** «смотри в `### 💥В. Тест` вторую и третью строку — при переносе текста влево, оно втыкается в префикс». Строки, на которых это пришло: `- (слово1 слово2 слово3)` и `- [ ] (слово1 слово2 слово3)`, выделено `слово3`, шаг влево.

**Причин оказалось две, и одна шире его примера.** Первая: у переноса не было стены на оформлении начала строки. Знак списка, чекбокс, номер, цитата и решётки заголовка тексту не принадлежат, а перенос считал их обычным соседом — на четвёртом нажатии выходило `слово3- (`, `- [слово3 ] (` и `1слово3. (`, то есть рвался сам знак. Тот же провал у посимвольного шага с включённым `Step out of the word` уводил буквы **в соседнюю строку**: `- один` + `- два` давало `- одиндв` + `- а`. Конец строки стеной был и раньше (перенос строки токеном не считается), а начала у неё не было вовсе.

**Вторая причина к оформлению отношения не имеет.** Правило о промежутках (10.13.238) знало одну сторону знака, и открывающая скобка уносила пробел не туда: `текст (слово3 слово1)` шагом влево давало `текстслово3 ( слово1)` — слово прилипало к соседу слева, а скобка отрывалась от своего содержимого. Теперь у знака есть сторона: `)` `,` `.` держатся за текст слева, `(` `[` `«` — справа, и знак уносит с собой **тот** промежуток, которым держится. Промежутков у пары ровно три, и правило по-прежнему их только переставляет.

**Что человек увидит.** `- (слово1 слово2 слово3)` шагом `слово3` влево: `- (слово1 слово3 слово2)` → `- (слово3 слово1 слово2)` → `- слово3 (слово1 слово2)`, и дальше ничего — знак списка не сосед.

**Чем закреплено.** Одиннадцать утверждений в `navigation_jumps_tests.js`: четыре формы оформления (список, задача, номер, цитата с отступом, заголовок), середина строки без оформления и четыре отрицательных контроля — перенос внутри строки, запятая со своей прежней стороной, строка без оформления и посимвольный шаг, который внутри строки работает как работал. Пять мутаций, каждая краснеет на своём утверждении: снять стену в границах, снять её в самом переносе, вернуть открывающему знаку левую сторону и снять обе проверки границ у посимвольного шага. Многострочная подделка редактора заведена тем же заходом — однострочная ухода в соседнюю строку не видит в принципе.

#### 10.13.238 Перенос выделенного: шаг до знака и переезд пробела (его пункт 7) (2026-09-22)

**Его слова** — два примера и условие: «перенос должен быть до символа», «`)` влево обязана дать `(слово1 слово2) слово3`», «я хочу испытывать комфорт от этой команды».

**Правил два, и оба узкие.** Первое: сосед отдаёт свой край из скобок, кавычек и знаков конца предложения отдельным шагом — тот край, который ближе к выделенному. Второе: пробел перед парой и пробел между её половинами меняются местами вместе с половинами, и только когда одна из половин целиком из тех же знаков.

**Чего правило не делает.** Не добавляет и не убирает пробелов; не трогает `#`, `/`, `-`, `|`; не разбирает язык. Край с парными знаками остаётся целым — иначе `[[test1]]` разорвался бы, и мутация показывает ровно это: `[[test1 123]]`.

**Почему обход строки тут молчит.** `line_matrix` сравнивает, что кладут на строку две дороги — панель и команда; перенос выделенного ни одна из них не делает. Числа до и после правки совпали посимвольно, и это назвал бы находкой только тот, кто не спросил, что стенд меряет (У-222). Разбор поведения — исключение № 144 в PRD 3.3.

**Его заказ `З-37`**, уточнённый `В-174` (вариант «а») и `В-176`: «оба, как заказывали».

Прочитав `app.js` 1.13.7, я увидел второе: метки разметки Obsidian снимает со строки заменой без виджета, пока выделение не перекрывает узел (У-256), и токены у неё свои — `formatting-link formatting-link-start`, `formatting-link-end`, цель `cm-hmd-internal-link`. **Кто выигрывает каскад — измерено браузером, а не выведено.** Наша пометка и пометка Obsidian накрывают один отрезок, и наш узел ложится **внутрь** её узла: значит цвет, объявленный на самом узле, выигрывает наследованием, и ни `!important`, ни поднятия веса не нужно — у обоих цена шире предмета (У-166). Перевернись устройство — гейт покраснеет: он спрашивает цвет у самого глубокого узла с теми же буквами, а не у узла с удобным классом.

Вторая — правило места каретки: скобки прячутся только пока выделение не перекрывает узел, и без этой половины подделка была бы строже оригинала (У-45), а второй цвет проверялся бы отсутствием предмета.

**Чем закреплено.** Три подмены браузерного шага, все три краснеют: цвет не ставится вовсе (`link-written-not-painted`), цель и скобки красятся одним цветом (`link-written-one-color`), правило стилей теряет свой узел (`link-written-loses-cascade`). Значения цветов в настройках страницы **разведены нарочно** (У-147) и оба отличаются от цвета подделки.

**Две находки по дороге, обе в моих инструментах.**

1. **Сборщик схемы считал скобки в комментарии записью.** `Decoration.replace({})` внутри объяснения к этой правке дало в схему пустое `{}` — и все семь шагов были зелёные: пустая запись не нарушает ни одного правила, она просто есть. Это У-96 в лоб: у своего разборщика обязана быть проверка **на симптом**. Теперь запись без `kind` роняет генерацию с именем группы.
2. **Подмена браузерного шага с неверным именем файла не применялась вовсе.** Лист стилей страница знает как `styles.css`; запись `src/styles.css` уходила в сборщик, где `.css` не грузится, и прогон печатал «проверка осталась зелёной — она не смотрит на то, что подменили». Я едва не снял по этому живое правило как мёртвое (У-151). Теперь такое имя роняет прогон.

#### 10.13.227 `Smart paste`: вставка из буфера по своим правилам (`З-31`, `З-32`) (2026-09-21)

#### 10.13.219 Перенос строк и нумерация списка: дело было в пометке транзакции (2026-09-20)

**Его замечание** (заметка тестов, пункт 11): «при move-lines up\down
нумерованного списка — при перемещении вверх и вниз нумерация не
восстанавливается — пример: я двигал sub-lines, и у меня нумерация под п.10 у
дочерней строки начинается с .3, а должна с 1».

**Первая догадка была бы «надо нумеровать самим», и она неверна.** Нумерацию
списков Obsidian правит сама, и правит не командой, а **фильтром транзакций**:
`sj(e)` в `app.js` 1.13.7 объявляет `transactionFilter`, который на каждое
изменение документа смотрит затронутые строки и дописывает своё изменение с
`userEvent: "input.renumber"`. У фильтра есть выход в самом первом условии, и
среди причин выхода стоит `t.isUserEvent("set")`.

**А `Editor.setValue` отправляет ровно эту пометку** — `n.dispatch({changes:
{…}, userEvent: "set"})`, там же в `app.js`. То есть перенос строк выключал
нумерацию не тем, что считал её неправильно, а тем, что говорил платформе «это
не правка человека». `Editor.replaceRange(text, from, to, userEvent)` четвёртым
аргументом принимает пометку, и без неё транзакция уходит непомеченной —
фильтр работает. Это У-181 в чистом виде: утверждение о платформе проверяется
её файлом, а не рассуждением.

**Что сделано.** `applyMove` в `navigation_runtime.js` (исключение к З3
№ 135) пишет перенос `replaceRange` по **окну изменившихся строк** —
от меньшего из «где блок был» и «где стал» до большего, — вместо
`setValue` со всем документом. Окно именно минимальное: фильтр нумерует от
затронутых строк, и замена документа целиком перенумеровала бы все списки
заметки разом. Тем же вызовом и тем же окном писал перенос строк **таблицы**
(`tableMove`) с самого начала, так что второго правила здесь не заводится —
наоборот, две половины одной команды сошлись.

**Цена измерена.** Стенд гоняет обе версии — из `HEAD` и из рабочего дерева —
на восьми формах заметки (нумерованный список с дочерними, простой текст,
заголовки и секции, фронтматтер, задачи, кодовый блок, таблица, пустые строки),
на каждой строке, в обе стороны, при трёх наборах настроек и с выделением и
без: **468 пар, расхождений 0** — ни в тексте, ни в курсоре, ни в выделении.
У самого стенда контроль: правка окна на одну строку короче даёт **273**
расхождения из тех же 468.

**Чем закреплено.** `tests/regression/move_line_renumber_tests.js`: документ
после переноса тот же, запись идёт `replaceRange`, и переписанное окно равно
окну разошедшихся строк. На коде до правки проверка краснеет на шести случаях
из шести — то есть видит именно этот дефект. Заодно поправлена подделка
редактора в `navigation_jumps_tests.js`: там `replaceRange` был пустышкой, и
после правки она показывала бы «команда промолчала» там, где команда сработала
(У-45).

**Чего это не лечит.** Оставшиеся четыре `setValue` в том же файле — перестановка
знаков и слов **внутри** строки. Нумерации они не касаются, и трогать их без
нужды значило бы править движок ради ровности.

**Второй заход того же дня: этого оказалось мало, и вот чем это измерено.** Он
вернулся с тем же тестом: «после move line up/down нумерация осталась сбитой —
`2. третий дочерний`, ожидалось `1.`». То есть фильтр платформы теперь работает,
но считает не так, как человек ждёт.

**Догадок больше не осталось — фильтр вырезан и прогнан.**
`tools/renumber_bench.js` достаёт `sj` из `app.js` **этой** машины вместе с его
помощниками, ставит расширением в настоящий CodeMirror (`@codemirror/state`
лежит в `node_modules`) и подаёт ему ту самую правку, какую пишет `applyMove`.
Прогон показал ровно две вещи:

  1. перенос строки **на одну позицию** платформа нумерует верно, а перенос в
     **начало подсписка** — нет: номер первого элемента она считает по
     **старому** документу, и строка приносит туда свой прежний номер. Его
     `2. 3. 4.` воспроизвелись в точности;
  2. **готовые верные номера фильтр не трогает.** Значит спорить с ним не надо —
     надо подать ему посчитанное.

**Что сделано.** `renumberOrderedWindow` в `shared_utils.js` — одно объявление
правила: номер элемента есть номер ближайшего старшего соседа **того же уровня**
плюс один, а нет такого соседа — единица. Уровень считается так же, как считает
Obsidian (`oj` в `app.js`): табуляция и каждые четыре пробела. `applyMove`
зовёт это на окне, которое всё равно переписывает, — то есть ни одной лишней
правки документа не появилось.

**Цена названа вслух и стоит в стенде отдельным случаем.** Список, который
человек нарочно начал не с единицы, при переносе его **первой** строки начнётся
с единицы: старшего соседа у неё нет. Перенос любой другой строки такого списка
его не трогает — измерено.

**Чем закреплено.** Шесть случаев `move_line_renumber_tests.js` (включая два
отрицательных контроля: строки без номеров не нумеруются, а внутри одного
уровня едет текст, а не номера) и шесть случаев стенда на настоящем фильтре.
У стенда контроль: снять нашу нумерацию — три расхождения из шести.

**Его замечание** (заметка тестов, тест 4): «при активации field-sub previous в

шла, и «панель жива» спрашивается у флага. Три подмены краснеют. Стенд сюда не
достаёт в принципе — он зовёт движок напрямую (У-56), поэтому в

предмет переехал в отдельное объявление `openTagWheelSession`, и оба стали
зелёными от того, что искать стало нечего (У-94). Обе проверки живут теперь
поведением.

#### 10.13.217 «Что изменилось» называет контролы и вкладывает их друг в друга (2026-09-20)

**Его замечание** (лист приёмки, строка `S8`): «смотреть setting
`pkm.fields.tags.fields` — это непонятно для пользователя, ты должен написать
название контрола (как в настройках плагина), чтобы пользователь понял, что

#### 10.13.216 Дописанный нами родитель круг дочернего поля не сужает (2026-09-20)

**Его замечание** (лист приёмки, строка `S11`): «для теста я добавил в
field=category несколько subvalues `#med`, `#old` и io-field-child=show always.
Однако в tagwheel в sub-field есть только значение `#new` (которое было
раньше). При этом если сначала выбрать соответствующий родительский токен в
field=cat в tagwheel, то после этого в field=cat-sub уже отображаются `#med` и
`#old`».

**Что он видел, измерено стендом на его `data.json`.** При `Parent Value` =
`Add the parent Value` круг стоял на месте:

| что стоит в `Parent Value` | `Cat_sub next` восемь раз подряд с `- текст` |
|---|---|
| `Leave the line alone` (умолчание) | `#new` → `#med` → `#old` → пусто → и по кругу |
| `Add the parent Value` (его случай) | `#work #new` → `#work` → `#work #new` → … |

**Причина одна на обе дороги.** Родителя на строку пишем мы сами, следом за
долистанным значением; на следующем нажатии он уже лежит на строке, и обе
дороги считали его выбором человека — в команде это было условие
`freeOfParent = … && !parentId`, в панели то же условие внутри `cycleValue`.
Отбор по нему оставлял у поля одного ребёнка, и круг схлопывался в пару
«значение — пусто». Его обход «сначала выбрать родителя» показывал ту же
причину с другой стороны: при выбранном им родителе отбор законен, и потому
там всё выглядело правильно.

**Правило, которое объявлено вместо условия.** Значение родителя, выведенное из
выбранного ребёнка, сведений не несёт — это наше эхо, а не его выбор.
Спрашивается это одним объявлением на обе дороги,
`parentValueEchoesChildValue` в помощниках правил: родитель наш, когда он равен
тому, что мы сами дописали бы нынешнему значению дочернего поля. Пока значения
у дочернего поля нет, родитель принадлежит человеку и отбирает по-прежнему —
это его прежнее решение (10.13.215), и разрешение `Show always` его не
отменяет.

**Починка открыла две следующие формы, и обе закрыты тем же заходом** (У-174).
Первая: команда напечатала значение дважды — `- #home #med #med`. Карта «какие
токены принадлежат дочернему полю» собиралась при **нынешнем** родителе и знала
одно значение из трёх; перекладывание не находило долистанного токена на строке
и дописывало его вторым разом. Карта отвечает на вопрос о принадлежности, а не
о допустимости (У-177), и у поля с разрешением `Show always` она родителя не
спрашивает. Вторая: на пустом месте круга наш родитель уходил со строки, а знак
задачи, который ставило **его значение**, оставался — `- [b] text` вместо
`- text`. Знак снимается тем же механизмом, что и у любого другого поля: полем,
чей выбор снят этим действием, становится родитель. Что знак не возвращается к
написанному человеком — правило дома, а не следствие правки: у обычного поля
команда на пустом месте круга даёт ровно то же, и это измерено тем же прогоном
на родителе.

**Чем закреплено.** Четыре проверки — две на дороге панели
(`prerequisite_runtime_limits_tests.ts`) и две на дороге команд
(`status_runtime_behavior_tests.js`), — и у каждой своя покрасневшая подмена,
восемь на восемь. Прежние проверки нажимали **один** раз, и дефект за этим не
виден никогда: он живёт со второго нажатия (У-104).

**И обход строки получил третью половину — круг дочернего поля.** Свойство
своё, ни одной дороге не принадлежит: круг обязан показать все значения поля и
замкнуться. Сверкой двух дорог это не ловилось — сломанные одинаково, они
сходились (У-194), и обход был зелёным 0 из 234 всё время, пока дефект жил.
Положительный контроль: на коде до правки третья половина краснеет **26 из
26**, после — 0.

**Обход строки** на его настройках остался 0 из 234, с `--split` — прежние 7 из
234 и 4 из 211 на втором нажатии (`Ф-8`, число уточнено прогоном).

что это и зачем. Уточнение оказалось короче правки: **револьвер уже работает
именно так**, у каждого Field и в обе стороны. Измерено командой на его
настройках: `previous` с пустой строки даёт последнее значение, дальше предыдущие
по списку, потом пустая, потом снова последнее; `next` идёт тем же кругом в другую
сторону. Пустое место — часть круга. Единственный не-сегодняшний вариант («круг
без пустого места») отнимал бы у него способ снять значение прокруткой, и он
сказал: «про края списка контрол не нужен — он должен работать так всегда».

**Что стало в панели настроек.** Ряд `Child Field` у Field с дочерним стал
выпадающим списком из трёх положений вместо `Yes`/`No`: `Show always`,
`After parent` (умолчание — так поле работало всегда) и `Hide`. При `Show always`
под ним появляется второй ряд, `Parent Value`: `Leave the line alone`
(умолчание) или `Add the parent Value`. Оба ряда — **у каждого Field свои**, как
он и просил.

**Где живёт настройка и как доезжает до движков.** Включённость осталась там, где
была, — в `active`/`enabled` Order, её читает рантайм и читают соседние контролы;
третье положение добавляет к ней **одну булеву карту** `subWithoutParent`, а не
второй ответ на вопрос «включён ли». Родитель — вторая карта, `subAddsParent`.
Дальше настройка едет к движкам не сама: `pkm_order_config.js` ставит её
свойствами **на определение поля** (`freeOfParent`, `addsParentValue`), потому что
и панель, и команды спрашивают разрешение **у поля** — общего конфига у этого
объявления нет.

**Правило предусловия правлено в одном месте.** `isFieldPrerequisiteMet`
отвечает `field.freeOfParent === true` там, где прежде отвечал `false`: у поля
без значения у родителя. Объявление одно на обе дороги (У-122), и потому панель
и команды получили разрешение одним изменением. Остальное предусловие не
тронуто: когда у родителя значение **есть**, названный список решает по-прежнему
— это его прежнее решение, и оно закреплено отдельным утверждением.

**Команда листает весь список, а не детей первого родителя.** Прежде на строке
без родителя команда дочернего Field молча ставила родителю **первое** значение и
листала только его детей. Теперь при разрешении родитель не трогается, а список
берётся у `getAllowedSubValues(field, "")` — он без родителя не отбирает и отдаёт
значения по `order`, то есть той же чередой, что показывает панель.

**Родителя дописывает одно объявление на две дороги.** «Какому значению родителя
принадлежит это значение» спрашивается у `parentValueIdForChildValue` в
помощниках правил; команда и панель зовут его же. Разойтись двум дорогам здесь
уже стоило заказчику дописанного значения (10.13.214), и второй копии тут не
будет.

**Первая сборка была мертва, и нашла это не проверка, а стенд.** Настройка
доезжала до поля в конфиге и **не доезжала до движков**: `normalizeField` в
`tagwheel_rules_normalizer.js` собирает поле для движков **перечислением**
свойств, и свойства, которого в перечне нет, движки не видят вовсе (У-192).
Команда молчала при включённой настройке. Теперь перечень знает оба разрешения, а
дорогу целиком — конфиг → `ensureBehaviorModesFromOrder` → `buildRulesForEngines`
→ поле — держит утверждение в `rules_from_settings_tests.ts`; подмена перечня
краснеет.

**Измерено на его настройках** (`node tools/line_bench.js`, копия его
`data.json` с включённой настройкой):

| что стоит в настройках | `Cat_sub next` на `- текст` |
|---|---|
| `After parent` (умолчание) | строка не тронута, сказано `Cat_sub waits for Category: set it on this line first` |
| `Show always` + `Leave the line alone` | `- #new :: текст` |
| `Show always` + `Add the parent Value` | `- #work #new :: текст` |

Обход строки на его настройках остался **0 из 234** (умолчание не менялось), с
`--split` — те же 4, что записаны находкой `Ф-8`. Проверок добавлено семь, и
каждая краснеет своей подменой: не читается разрешение в предусловии (панель),
не читается оно в команде, список берётся у первого родителя, родитель не
дописывается командой, родитель не дописывается панелью, перечень свойств теряет
оба разрешения.

#### 10.13.214 Панель больше не дописывает значение дочернего Field (2026-09-19)

**Его слово:** «нет, не надо дописывать и исключи это дописывание из tagwheel.
Такое может быть, если я вызываю команду Category_sub next не выбрав value из
field Category — в этом случае у меня должен быть скроллинг по всем sub-values
этого field».

**Предмет нашёлся обходом строки, а не глазом.** После того как он 2026-09-19
переставил Field `Cat` из правого Block в левый, `node tools/line_matrix.js`
показал **шесть расхождений из 234** — все одной формы: на строке стоит
значение дочернего Field, родителя нет, команда оставляет строку как есть, а
панель дописывает то же значение вторым разом в правый Block.

**Причин оказалось две, и обе измерены пробами внутри сборки строки.**

1. **Сторону дочернего Field спрашивали его собственным ключом.** Ключа
   `<name>_sub` нет ни в `order.left`, ни в `order.right` — `normalizePkmOrder`
   выбрасывает его оттуда нарочно, — и `panelForTagKey` отвечал **умолчанием**,
   а умолчание у панели `right`. При этом звавший (`relocateTagLikeByOrder`)
   правильный ответ уже знал и спрашивал ключом родителя: правило было
   объявлено дважды и разошлось молча (У-122).
2. **Карта токенов дочернего поля выходила пустой.** Отбор значений по
   родителю сравнивал **невыбранного** родителя со списком допустимых — пустая
   строка не совпадала ни с чем. Пустая карта значит «в строке чистить нечего»,
   и прежнее значение оставалось на месте, а выбранное дописывалось.

**Правка узкая, и её ширину назвала покрасневшая проверка.** Первая версия
отдавала сторону родителю **всегда** — и уронила утверждение о значении
спрятанного поля (10.13.188): у дочернего Field со своим ключом в `left` или
`right` сторона своя, это прежнее его решение. Теперь родитель отвечает ровно
там, где иначе ответом было бы умолчание.

**Измерено.** Обход строки: **6 из 234 → 0**; с разведёнными разделителями
(`--split`) **10 → 4**, и остаток — другого рода, записан находкой. Стенд на
его конфиге до правки давал `- #new :: текст :: #new`, после — входную строку.
Две подмены краснеют: сторона по своему ключу и возвращённый отбор по
невыбранному родителю.

**Вторая половина его слова спрошена, а не сделана.** «Скроллинг по всем
sub-values, когда родитель не выбран» отменяет его же прежнее решение: команда
дочернего Field при невыполненном предусловии говорит человеку
«`Cat_sub` waits for `Category`: set it on this line first» (В-137, правило
107). Новое слово, переворачивающее прежнее без объяснения, спрашивается до
правки (правило 154) — вопрос задан.

#### 10.13.213 Ключи без читателя в его файле и настройки, не доехавшие до Transform (2026-09-19)

**Его заказ:** «я хочу, чтобы ты проверил, что в data.json и в генерируемых
файлах бэкапа нет других мёртвых веток. В целом ты ранее выполнял аудит кода, я
ожидал, что после его завершения и выполнения всех выявленных проблем подобных
ситуаций не будет».

**Почему ревизия 2026-09-18 этого не нашла — ответ, а не оправдание.** Она
меряла код: мёртвые экспорты, тихие отказы, копии правил, объявленное и
незваное. Ключ, который лежит в файле **человека** и не читается ничем, — другая
сторона: не код без вызова, а данные без читателя, и её не мерил никто. Обещание
«таких ситуаций не будет» опиралось на меру, которой не было (У-236).

**Мера теперь есть:** `node tools/dead_keys.js <файл>`. Читателями считаются два
источника, и оба выводятся: пути строк панели (схема выводится из прототипа) и
все литералы вида `a.b.c` во всём `src`, снятые по маске, где комментарии
стёрты. У обхода **контроль до первого вывода** (У-119): подсаженная мёртвая
ветка обязана быть названа, живая настройка — нет; не сошлось — печатается
отказ, а не список.

**Первый прогон соврал бы, и это тоже измерено.** Литералы `keepV2("…")` и
списка снятых ключей — это бухгалтерия переезда, а не чтение: считая их
читателями, обход объявлял живым всё, что когда-либо переезжало, и кеш
конфиг-заметки не находил вовсе. После разделения бухгалтерии и чтения в его
файле нашлось **35 листьев без читателя**: три ключа конфиг-заметки, семь
ключей состояния старой панели, вид редактора Fields, тумблер `newSettingsPane`,
три листа приставок формы версии 1 — и двадцать один ложный, у которых чтение
идёт свойством, а не литералом. Ложные названы поимённо в самом обходе, с
адресом чтения; настоящие сняты списком `REMOVED_V2_KEYS` вместе с их
объявлениями в нормализации. Стало **0 из 346**.

**И то, ради чего стоило искать.** Обход показал, что ветку `pkm.prefixRules`
никто не читает литералом, — а читает её Transform, свойством, и читает
**форму версии 1**: три значения приставок панель пишет на пути
`pkm.prefixPriority.*`, и сводит их воедино `pkm_rules_shape`. То есть смена
`Decide by`, `Field order source` или `Parent or child wins` доезжала до всех
движков и не доезжала до Transform. Измерено на его `data.json`: панель
`by-checkbox-list`/`tag-over-subtag`, сборщик то же, старая ветка
`by-section`/`subtag-over-tag`. Починено одной строкой — Transform спрашивает
общий сборщик; условие «нет ветки — нет разбора приставки» оставлено прежним
нарочно (У-164).

**Чем закреплено.** `dead_config_keys_tests.js` (четыре проверки: контроль
обхода, конфиг умолчаний, конфиг после переезда с версии 1 и заметка копии) и
проверка поведения Transform, спрашивающая **шов**: разрешителю приставки
отдаётся подделка, и она запоминает полученные правила. Первая версия этой
проверки спрашивала сборщик — и была зелёной при возвращённой подмене, то есть
проверяла не тот предмет.

#### 10.13.211 Кегль и уровень написанного в Block (2026-09-19)

**Его замечание со скриншотами:** «с плагином при tags-text-size-left и
tags-text-size-right = 100 текст в left/right block кажется больше, чем в text
block (или смещён ниже). При 100 текст в left/right block должен быть таким же
как в text block (находиться на том же уровне)».

**Кегль считался от литерала.** `computeTagVisualStyle` брал `14 * доля`, а у
Obsidian кегль текста шестнадцать (`--font-text-size` в `app.css`) и вдобавок
задаётся темой и настройкой размера человека. То есть на сотне процентов пузырь
рисовался **не тем** кеглем, которым написана строка рядом, и ни одна проверка
этого не видела: подделка страницы объявляла редактору те же шестнадцать, а
сравнения с ними не было (У-235). Теперь мера приходит от того, кто рисует —
`getComputedStyle(view.contentDOM).fontSize`, — и берётся **у своей строки**: у
заголовка кегль свой, и `Block` на заголовке обязан следовать ему. Кегль считается
дробно: у темы он бывает нецелым (16,8), и округление до точки давало бы промах
на его же требовании.

**Уровень.** `vertical-align: middle` ставит середину ящика на середину высоты
`x`, а не на середину написанного: промах **1,58 точки**, обмерено браузерным
шагом на 26 парах «пузырь и текст одной строки». Заменено вычисленной величиной:
подъём — половина разницы кеглей строки и значения. На сотне он ноль, то есть
значение стоит базовой линией — ровно на уровне текста, как он и просил; мельче
— подъём ровно тот, которого не хватало `middle` (это его же прежнее слово
2026-09-16 про мелкий кегль). То же правило получили ссылка и эмодзи-элемент:
вопрос у них один (У-206).

**Мера прежде врала дважды, и обе поправки записаны.** Сначала она сравнивала
ящик пузыря с ящиком выделения текста — разные рода ящиков, систематическая
единица на ровном месте. Потом брала текст, который сам перенёсся: объединение
рядов даёт середину посреди пустоты. И третье: сравнивать надо с буквенной
строкой, а не с той, где эмодзи — его глиф выше, и середина уезжает сама.
После трёх поправок промах **0 на 30 парах**.

**Цена лекарства названа** (У-166). Подмена `vertical-measured` перестала
различать два пути — значение теперь стоит там же, где текст строки, и «из
измеренного» с «из ряда» сошлись: 0,62 против 1,01, порог между такими числами
был бы порогом на шум машины. Подмена снята с объяснением, а область закрыта
двумя новыми утверждениями: «написанное в Block на уровне текста строки» (30
пар, промах 0) и «подложка серединой на написанном своего ряда» с порогом 2 — на
нём прежнее состояние даёт 3,06, а подмена `row-height-default` — 3,9…6,2.

#### 10.13.210 Автокопия: чувствительность, уведомление, коллаут и мёртвая ветка (2026-09-19)

**Три его замечания по `S5` и один его вопрос, и все четыре — об одном заходе.**

**Первое: «autosave слишком чувствительный».** Его слова: «он делает
автосохранение, даже если изменилась активная панель в настройках
`ui.activeSettingsTab` — это лишнее, должно автосохраняться только при
изменении настроек (изменение значений контролов)». Причина измерима и
поучительна: сравнение шло через `selectParts`, а тот отбирает **не** ветки
вкладок, а «всё, кроме чужих вкладок и локального для устройства». Верхняя ветка
`ui` не принадлежит ни одной вкладке — и проходила насквозь. Имя функции
обещало отбор, а тело делало исключение: читать надо было тело (У-233).
Исправлено свойством, а не именем ветки: сравниваются ровно те ветки, которые
названы вкладками (`PART_BRANCHES`). Проверка спрашивает обе стороны правила —
переключение вкладки молчит, правка контрола снимает копию.

**Второе: «хочу, чтобы при создании autosave об этом возникало уведомление».**
Сделано: `Settings autosaved to {0}` с путём заметки, ключ в каталоге текстов,
шов `notify` в загрузке. Отрицательный контроль рядом: копия не снималась —
человека не беспокоим.

**Третье: «хочу, чтобы в заметке бэкапа текст „Write anything here…“ был
коллаутом».** Сделано разметкой Obsidian (`> [!note]`), двумя строками; разбор
заметки это не задело — блок настроек лежит ниже, и проверка спрашивает и то и
другое.

**Четвёртое, и это не замечание, а находка:** «я изменил `data.json`, но при
открытии плагина я этих изменений не увидел в настройках». Он правил
`pkm.fields.taxonomy.tagWheelConfig.wikilinks.Project.bySection.Project.defaults`.
**Плагин его файл принял** — правка в файле осталась, ничего её не затирало, — но
эта ветка **не читается никем**: во всём `src` слово `taxonomy` встречается в
двух файлах (карта маршрутов и нормализация), а `bySection` — ни в одном.
Значения Field, которые панель показывает, лежат в
`pkm.fields.links.fields[].values[].token`, и там ровно то, что он видел на
экране.

**Ветка снята, потому что она врала.** Это разобранный кеш конфиг-заметки
TagWheel, снятой 2026-09-03 его же решением В-28: 589 знаков в его файле, у
которых нет ни читателя, ни контрола. Снятие идёт списком `REMOVED_V2_KEYS`, то
есть на каждом проходе и для файла любой версии; вернуть его можно из любой
копии настроек, включая автокопии, уже лежащие в его папке. Урок общий: **ключ
без читателя в файле человека — это не мусор, а ловушка** (У-234), и у неё есть
цена: его вечер и три его сообщения.

#### 10.13.209 `Autosave`: копия настроек при открытии плагина (2026-09-19)

**Его заказ (З-11)** и **его же ответ на вопрос** (`В-147`, тот же день): копия
снимается при открытии плагина, если файл разошёлся с последней автокопией —
второй из вариантов, которые он набросал сам.

**Цена выбора названа числами до вопроса, и прежняя была неверной.** Я писал
«копия на каждую запись — это сотни файлов при одной протяжке слайдера»; это не
так, и мера простая: запись отложена на 250 мс, таймер перезапускается на каждой
правке (`scheduleSave`), то есть протяжка доходит до диска **одной** записью.
Настоящие числа на его `data.json`: полная копия — 23 223 байта и 926 строк;
копия на каждую правку при двадцати правках за вечер — 454 КБ; копия на
открытие — одна заметка на сессию. Неверная цена делает выбор недействительным
(У-171), поэтому вопрос задан заново и с этими числами.

**Что этот момент ловит и чего не ловит.** Ловит файл, пришедший снаружи:
синхронизация, второе устройство, копия из другого vault — ровно тот случай, из
которого заказ и вырос (его замечание `C1`). И каждая сессия начинается со
снимка «как было до сегодняшних правок». Не ловит откат на один шаг внутри
сессии — это второй вопрос, и на него отвечает команда `Undo last settings
change`. Слить их в один значило бы получить ту самую простыню из заметок, на
которую он жалуется в соседнем письме про changelog.

**Что сделано по его словам дословно.** Тумблер `Autosave` в группе `Backup`
(умолчание — выключено: заметки в vault человека плагин без спроса не пишет).
Копия **максимальная** — все семь вкладок и хоткеи плагина. Приставка
`_autosave` в имени файла, и она своя, не `Autogenerated`: тем помечены копии
перед восстановлением и сбросом, то есть путь назад от действия человека.
Раздел `What changed` стоит **под разделом человека и над блоком настроек** — там,
где он и сказал.

**«Что изменилось» — путями, и это выбор.** Имя контрола живёт в схеме панели, а
копия снимается при загрузке, когда панели нет вовсе; путь человек видит в
`Advanced → Options IDs`, то есть он ему не чужой. Строк не больше двадцати,
остаток называется числом — та же причина, по которой в рассказе о выпуске
появилась нумерация.

**Предел — десять новых автокопий**, старые уходят в корзину vault, а копии,
снятые руками, не трогаются вовсе. Числа он не просил, и лишняя строка в панели
стоит дороже разумного умолчания (У-156); сказано это вслух в подсказке и в
отчёте.

**Дом правил — `settings_backup.js`:** имя с приставкой, разбор заметки, список
изменений и отбор устаревших копий лежат там же, где всё остальное про копии.
Свой файл — `settings_autosave.js` — держит только решение и шов к vault.

**Сравнение идёт с тем, что лежит в заметке.** `buildBackupNote` отбирает ветки
по вкладкам, и сравнение **полного** конфига с этим отбором расходилось бы
всегда — то есть копия снималась бы при каждом запуске. Это У-147, только
совпадающей стороной здесь была бы моя невнимательность; подмена «сравнивать
полный конфиг» краснеет.

**Чем закреплено.** `settings_autosave_tests.js`, девять проверок: тумблер,
первая копия, совпадение, расхождение с названными листьями, предел, нечитаемая
прежняя копия, отсутствие шва, отказ записи — и **водитель шва** (правило 124):
у `autosaveVaultSeam` один звавший, и тот в загрузке плагина, куда из набора не
дотянуться, поэтому шов исполняется проверкой на поддельном `app`. Подмен три —
тумблер не спрашивается, сравнение по полному конфигу, предел снят, — и краснеют
все три, каждая на своём утверждении.

#### 10.13.208 Окно «что изменилось»: форма пункта, пропущенные выпуски, ссылка (2026-09-19)

**Его замечание под `N4`, четыре части:** «стало лучше, но всё равно плохо —
текст с разрывами на предложениях; префикс исправлений должен быть нумерацией
(чтобы было видно сколько пунктов изменено); текста много — нужны буллиты с
понятным, но лаконичным описанием, чтобы было понятно обычному человеку, что
изменилось… этот changelog должен дублировать changelog.md в репозитории…
changelog в obsidian показывает только изменения последней версии (или лучше N
версий с последнего обновления плагина)… также в плагине должна быть ссылка на
changelog.md в репозитории github… Я не очень опытный в github, возможно я
изобретаю велосипед — тогда подскажи более оптимальный и рациональный вариант».

**Разрывы — не вкус, а правило платформы.** Obsidian показывает одиночный
перевод строки переносом, и прочитано это в `app.js` 1.13.7, а не выведено:
умолчание `strictLineBreaks` там `!1`, а отрисовка ставит
`globalOptions.breaks = !getConfig("strictLineBreaks")` — то есть переносы
включены ровно у того, кто настройку не трогал. `CHANGELOG.md` был свёрстан по восемьдесят знаков, как любой документ
репозитория, — и приезжал человеку лестницей. Лечится это не разборщиком и не
правилом стиля, а формой источника: **пункт — одна строка**. Это же его старое
слово о документах, которые он читает («предложения должны быть все без
разрывов»), и теперь оно исполняется машиной, а не памятью.

**Нумерация и лаконичность — форма файла, а не окна.** Дом текста один
(`CHANGELOG.md`, 10.13.169), поэтому обе половины его просьбы сделаны **в нём**:
каждый пункт стоит под номером, и номера идут насквозь по выпуску — так видно,
сколько пунктов тот затронул. Файл переписан целиком: 106 пунктов, у каждого
одна строка и предел в четыреста знаков. Подробности никуда не делись — они и
раньше жили в реестре отчётов и в этом разделе PRD, а в рассказе для человека
были лишними.

**Сторож формы — `release_notes_tests.js`**, и он написан по признаку дефекта, а
не по образцу: обход разделов выпусков ищет три вещи — продолжение пункта на
следующей строке, пункт без номера и пункт длиннее предела. Порог рядом: пунктов
обязано найтись не меньше десяти, иначе обход ищет не то (У-200). Положительный
контроль был получен даром — проверка была написана **до** переписывания файла и
покраснела на прежней форме.

**Пропущенные выпуски.** Прежде окно показывало раздел только своей версии;
теперь — все разделы строго новее той версии, о которой человеку рассказывали в
прошлый раз, новые сверху. Сравнение версий своё (`compareVersions`): форма
номера задана `docs/dev/VERSIONING.md`, три числа и хвост беты через дефис, и хвост
слабее выпуска. Предел — пять разделов, и он нужен другой половине того же
письма: обновившийся через десять выпусков получил бы ту самую простыню.
Дальше — ссылка. Прежней версии можно и не знать (человек мог не обновляться с
тех дней, когда окна не было): тогда рассказывается про одну нынешнюю, а не про
всю историю.

**Ссылка — в двух местах, и адрес у неё один дом.** В самом окне (строка между
текстом и кнопкой) и кнопкой `Changelog` в группе `General → Help`: окно
показывается один раз на версию, и ссылки в нём человеку хватает ровно один раз.
Адрес объявлен в `release_notes.js` и читается обоими; сторож спрашивает
свойство, а не список файлов — во всём рантайме адрес встречается ровно один
раз. Кнопка отдаёт его шву `openExternal`, а не зовёт `window.open` по месту: в
прогоне окна браузера нет вовсе, и проверке иначе нечего было бы спросить, кроме
отсутствия отказа.

**Про «изобретаю ли я велосипед» — нет, это ровно общая практика**, и она здесь
уже стояла: накапливающийся `CHANGELOG.md`, новые версии сверху, у каждой
версии свой раздел (формат Keep a Changelog), и выпуск, который GitHub сам
показывает отдельной страницей по тегу. Единственное, что он мог бы выбрать
иначе, — **куда ведёт ссылка**: сейчас на сам файл в `main`, а можно на страницу
релизов, где GitHub рисует те же разделы по выпускам. Разница на экране есть,
работа — одна строка, и решает он: вопрос задан в конце сессии.

#### 10.13.207 `Stripe direction`: какой Block получает полосу (2026-09-19)

**Его заказ (З-12):** «tags-block-fill при ON — добавить под этим контролом
дополнительный контрол `Stripe direction` с выпадающим списком (Left, Right,
Both) для определения направления места возникновения полоски, по умолчанию
both. При left — полоска возникает только в left block, при right — только в
right block».

**Где объявлено правило.** Один раз — `blockFillZoneWanted` в

получил зону) и предпросмотр панели (ставит класс стороны). Дом у правила один
нарочно: правило вида, поправленное у одной отрисовки, вторую оставляет на
прежнем ответе (У-217), и полоса этот урок уже один раз купила — кегль,
прозрачность и выравнивание пришлось учить составу Block по отдельности.

**Сторона названа классом, а не переменной.** `io-line--blockfill-left` и

одна, сколько бы полос ни рисовалось. Имена написаны литералами целиком, а не
собраны из куска и зоны: имя класса — такое же объявление правила (У-103), и
собранное по частям не находит ни греп, ни сверка двух отрисовок.

ей от рукописного `data.json` не за что; границы при этом держит нормализация
(`oneOf` на трёх значениях), а не панель.

заметке (`block_fill_tests.js`, три положения подряд — на одном правило «красить
всегда обе» было бы зелёным), сверка двух отрисовок по имени класса
(`preview_parity_tests.ts`, обход вместо списка) и закрашенная сторона у
браузера (`check_panel.js`: спрашивается не класс, а фон, потому что вопрос у
человека именно про фон). Подмен три: снятый отбор в слое, правило, всегда
отвечающее «да», и предпросмотр, не читающий направление, — краснеют все три, и
каждая на своём утверждении.

**Что увидит заказчик.** Новая строка под тумблером полосы, три значения, `Both`
по умолчанию — то есть у того, кто ничего не менял, вид не изменился ни на
точку.

вторая куплена ошибкой выше: пометка на месте **и** файл внутри программы. Снятая
пометка оставила бы прогон типов зелёным, и никто бы не заметил (У-94).

**Два сторожа покраснели на этой работе, и оба по делу.** Проверка объяснений без
предмета — дважды: я вставил второй блок комментария между объяснением и функцией, и
объяснение осталось стоять над пустотой (У-96); и второй раз — на имени в обратных
кавычках, которого в файле нет. Оба случая — та самая форма, ради которой сторож
заведён.

**И мой собственный обход соврал третий раз за сессию.** Разбор образцов `include` 
подставлял выражение на месте двойной звёздочки, а следующая замена звёздочек портила
уже подставленное. Поймал это положительный контроль внутри проверки — образцы
перестали находить даже файлы слоя настроек (У-142).

#### 10.13.202 Панель на очень длинной строке: место названо и снято (2026-09-19)

**Строка ревизии — `Р-12`, и задача была «назвать место», а править — только
если место одно.** Место оказалось одно, и вне З3.

**Чем найдено.** Профилировщик V8 (`node:inspector`), новый режим стенда —
`node tools/line_stress.js where`. Своей обёртки вокруг экспортов нет нарочно: она
видит только вызовы через объект модуля и своё же время приписывает предмету, а V8
считает **собственное** время. Сравниваются две длины, и находка — не самая дорогая
строка, а самое крутое отношение.

| Место | мс при 2 000 | мс при 20 000 | рост |
|---|---|---|---|
| `commonPairs` в `src/core/panel_line_write.js` | 13 | **1009** | x80 |
| сборщик мусора | 9 | 520 | x55 |
| `planPanelLineWrite` там же | 8 | 436 | x55 |
| `hasFieldTokens` в `line_pipeline.js` | 6 | 81 | x13 |

Длина выросла в десять раз: всё, что круче, — находка. Круче всего одно место, и
второе с третьим — его же следствие (сетка на 3 300 × 3 300 клеток и мусор от неё).

**Что сделано.** Наибольшая общая подпоследовательность слов считается только по
**середине**: совпавшие начало и конец в сетку не попадают. Приём точный, а не
приблизительный — при совпадении первых слов есть оптимальная подпоследовательность,
которая с этой пары начинается; то же у последних.

**Расхождение измерено до правки и равно нулю.** 4 737 настоящих пар «строка человека
/ вид панели», записанных с обхода строки обеими дорогами (и с `--split`) и с
пробы на прочность: планы совпали целиком, поле в поле.

**Контроль к мере сначала не прошёл, и это стоило одного прогона.** Первая подмена
снимала обрезку хвоста — и расхождение получилось нулевым, потому что приём сохраняет
результат по построению: подменена была скорость, а не правило (У-151). Вторая подмена
меняет разрешение ничьей при обходе сетки и даёт расхождение на 310 парах.

**Что стало с ценой** (один прогон, эта машина, его `data.json`):

| Длина строки | Панель до, мс | Панель после, мс |
|---|---|---|
| 2 000 | 11 | 16 |
| 5 000 | 27 | 21 |
| 10 000 | 117 | 29 |
| 20 000 | **1 263** | **49** |

**Сторож — `tests/regression/panel_line_write_tests.js`, и цена в нём сторожится
отношением, а не миллисекундами**: порог в миллисекундах зелен на быстрой машине и
красен на медленной (У-78). Обе величины снимаются одним прогоном. **Первый порог был
слишком широк**: квадрат прежняя версия проходила (x89 при пределе x100), то есть

проверен в обе стороны: новая версия даёт около x3…x9, прежняя x66…x89.

**Найденное тем же заходом и не моё.** На строке в **40 000** знаков команды
важности падают: `Invalid regular expression: too large` — где-то целая строка
уходит в выражение как один токен. Падение **старше правки**: воспроизведено на
рабочем дереве до неё (У-187). Форма дописана в обход тем же заходом (У-185), и теперь
проба на прочность честно печатает два падения вместо тишины. Сама починка — строка

**Обход строки: 0 из 234 до и после**; `--split` — 24 до и 24 после, то есть
правка его не двигала.

#### 10.13.201 «Надо ли перерисовать» в слое оформления: объяснено, а не выровнено (2026-09-19)

**Строка ревизии — `Р-8`, и сама ревизия оставляла выбор: «объяснить или
выровнять».** Выбор сделан измерением, а не вкусом.

**Что намерено.** Пробой со счётчиком на шве записи: обычная запись контрола панели
даёт **ноль** вызовов `refreshOpenEditors`, патч своего блока — **один**,
правка с причиной, которую видит одна панель, — **ноль**. У счётчика контроль: он
и правда считает (второй случай).

**Что из этого следует.** У настройки, которая живёт в декорации, а не в переменной
CSS, единственный путь до открытой заметки — ближайшее обновление редактора. Ответ
«перестраивать всегда» у двух расширений и есть этот путь; охрана по флагам его
сузила бы. Выравнивать четыре ответа в один, не тронув шов выше, значило бы починить
стиль и сломать доставку.

**Три флага — не то же, что «всегда», и это тоже прочитано у платформы.**
`selectionSet` значит «в транзакции была селекция», а не «она изменилась»
(`get selectionSet() { return this.transactions.some(tr => tr.selection) }` в
`@codemirror/view`), поэтому толчок из `refreshOpenEditors` их будит. А
транзакцию из одних эффектов — `reconfigure` компартментов, которым тот же
толчок начинается, — не будит ни один из трёх.

**Что сделано.** Объяснение — одно, на все четыре ответа, и стоит оно у первого из
них (`createTagVisualDecorationExtension`): таблица «кто как отвечает», причина
каждого ответа, измеренная цена «всегда» (0,45–0,56 мс на сборку тегов, 0,08–0,10 на
полосы, около 5 мс в секунду при наборе) и указатель на настоящую работу.

**И измерение стало пином** — `tests/regression/settings_refresh_road_tests.ts`. 
Пока числа такие, «всегда» верно; поменяется шов — проверка покраснеет, и следующая
правка оформления будет сделана с открытыми глазами, а не по памяти (У-145: число
живёт в прогоне).

**Настоящая работа названа отдельно.** Обычная запись контрола до пересборки заметок
не доходит вовсе — это шов, а не оформление; строка `Ф-4` в
`docs/dev/REMAINING_WORK.md`, и цену её решает его глаз.

#### 10.13.200 Перетаскивание строки списка объявлено один раз (2026-09-19)

**Это находка ревизии, строка `Р-11`.** Работа моя: оба файла вне З3, и
разрешения она не требовала — но порядок тот же, что у движков, потому что правило
одно и то же: **сводится только то, у чего расхождение измерено и равно нулю**.

**Что было.** Правило «строку списка можно взять за ручку и бросить на место другой»
— ручка, пять приёмников событий, два класса состояния — стояло дважды: в
`binder_view.ts` и в `order_lists.ts`, по 27 строк каждое.

**Расхождение измерено до правки и равно нулю.** Мера: взять оба куска, привести
три имени, которые отличаются законно (узел строки, откуда берётся подпись ручки, чем
задана перетаскиваемость), и сравнить побайтно. 1103 знака против 1094, после
приведения — совпадение знак в знак. У меры два контроля: нарочная порча куска обязана
дать расхождение, и приведение имён не должно съедать сам кусок.

**Третье место с перетаскиванием сводить было не во что, и это спрошено, а не
предположено** (У-159: «кто ещё отвечает на этот же вопрос»). В редакторе Fields
бросок принимают сторона и её подпись, и вопрос там другой — не «переставить строку
внутри списка по номеру», а «перенести поле на эту сторону и в это место»; там свои
`stopPropagation` и своя запись через модель. Общего — только имена событий.

**Дом — `src/ui/settings/custom/row_drag.ts`, `attachRowDrag`.** Состояние
списка («кого сейчас тащат») передаётся, а не заводится внутри: функция зовётся на
каждую строку, и своё поле сделало бы каждую строку слепой к остальным.

**Проверок две, и это не перестраховка** (У-195). Сведение копии делает сверку двух
дорог слабее: сломанный общий дом ломает обе одинаково, и «один список против
другого» больше ничего не покажет (У-194). Поэтому написаны **ожидание правильного
ответа** (дом зовётся напрямую, спрашивается каждое звено протокола броска) и
**проверка формы** (ни один звавший не завёл тело обратно). Мутации показали, что они
и правда про разное: поломка дома красит поведение у обоих живых списков, возврат
копии — только форму.

**Непокрытая сторона покрыта тем же заходом.** У Binder перетаскивание проверялось с
самого начала, у списков порядка — нет; после сведения она стала бы молчаливой
половиной. Теперь бросок идёт по настоящей отрисовке списка и кончается настоящей
записью в конфиг.

**Что увидит заказчик — ничего, и это цель.** Поведение не меняется по построению:
расхождение было нулевым, а единственный довод, которым списки отличаются (у Binder
строка тащится всегда, у списков порядка — по тумблеру), переехал в параметр и
проверяется с обеих сторон.
