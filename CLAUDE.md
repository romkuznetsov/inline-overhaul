# Inline Overhaul — что нужно знать до первой правки

Плагин Obsidian: навигация по строкам, инлайновые PKM-теги, TagWheel, оформление тегов, превращение строки в заметку. Идёт переработка слоя настроек по PRD.

**Главный документ — `docs/PRD_Settings_Overhaul_v1.md`.** Раздел 2 «Зафиксированные решения» (Р1–Р14) принят заказчиком и не пересматривается. Раздел 3 «Запреты» (З1–З8) сильнее всего остального.

## Правило первое: прототип нормативен

`docs/prototype/settings_prototype.html` согласован заказчиком (Р8) и является источником истины по структуре панели, всем видимым текстам и поведению своих блоков. Он открывается в браузере и работает без сборки.

Из него **выводятся**, а не пишутся руками:

| Что | Чем | Правится через |
|---|---|---|
| `src/ui/settings/schema/*.ts` | `npm run gen:schema` | прототип |
| Раздел 9 и Приложение B PRD | `python tests/prototype/update_prd.py` | прототип |
| `dist/**` | `npm run build` | исходники |
| `tests/prototype/v1_inventory.tsv` | — заморожен, фиксирует прошлое | не правится |

Правка сгенерированного файла руками не переживёт следующую генерацию. Хук `PreToolUse` это блокирует; гейты `gen_schema` и `update_prd` ловят расхождение, если хук обойти.

Порядок при любом изменении панели: **прототип → генерация → проверки → коммит**.

## Проверки

```
npm run lint          npm run gate            гейты слоя настроек на заглушке
npm run typecheck     npm run gate:prototype  7 проверок прототипа + расхождения
npm test              npm run install:test    сборка в тестовый vault рядом с репо
```

Все шесть шагов должны быть зелёными: их же гоняет CI. Проверки прототипа читают **результат рендера**, а не исходник: порядок значений в скроллере TagWheel, полосы на каждой строке, вычисленные значения YAML.

`tests/gates/phase.txt` — одно число, текущая фаза. При переходе к следующей фазе его надо поменять, иначе гейт молча пропускает проверки структуры.

## Правила текстов (раздел 7 PRD)

- **Сущности плагина — с заглавной** в любом месте фразы: `Field`, `Value`, `Bar`, `Prefix`, `Separator`, `Block`, `TagWheel`, `Binder`, `Transform`, `Smart Rules`. Слова Obsidian и обычного языка — со строчной: line, note, tag, template, hotkey (Р9).
- **Точка в конце видимой строки не ставится** (Р10). Внутри абзаца точки между предложениями остаются.
- Ссылка на команду, хоткей, настройку или значение оформляется как `<code>` (Ст11).
- Длинное объяснение живёт в `tip`, а не в `desc` (Ст12).

Гейт Г10 и Г17–Г19 проверяют это механически, в обе стороны.

## Слой настроек

Строится на **декларативном API Obsidian 1.13** (Р2): платформа берёт рендеринг, привязки, валидацию и глобальный поиск. Наше: схема как источник истины, хранилище через шов `getControlValue` / `setControlValue`, свои блоки через `render`, полоса вкладок своей вёрсткой (П-16).

Три вещи, на которых легко обжечься:

1. **Формы определений берутся из типов пакета `obsidian`, а не из документации.** Три бага подряд выросли из предположений: `extraButtons` это массив **функций**, у группы **нет** поля `desc`, `disabled` принадлежит контролу. В типах нашлось и то, чего нет в руководстве: `aliases` (ключевые слова для поиска) и `type: 'list'` (готовые списки с перетаскиванием и клавиатурой). Проверяйте по `node_modules/obsidian/obsidian.d.ts`.
2. **`getSettingDefinitions` вызывается часто** — никакого I/O внутри, описания кешируются.
3. **После записи значения определения надо пересобрать** (`update()`): платформа пересчитывает предикаты, но не определения, а от значений зависят и они.

Новая панель включается флагом `advanced.newSettingsPane` и **не подменяет старую**, пока в ней нет редактора Fields, живых предпросмотров, Binder, Smart Rules и справочника команд. Переключать человека на панель без половины инструментов нельзя.

## Окружение

- Windows, путь проекта с пробелами и кириллицей. Пути в командах брать в кавычки.
- Node 24 запускает `.ts` напрямую (стирание типов). Ограничение: **параметры-свойства в конструкторе** (`constructor(public x)`), `enum` и `namespace` не поддерживаются.
- **Heredoc в bash съедает обратные слэши и апострофы.** Патч-скрипты со сложными строками писать файлом, регулярки в них — без экранирования или через `chr()`. Это уже трижды ломало правки.
- В HTML прототипа лежат литеральные `—`, `→`, `⠿` и типографские кавычки: искать их через `chr()`, а не `—`.
- Правки в прототипе делать **функциями целиком по имени**, а не участками между маркерами: нарезка по маркерам однажды удалила четыре рендерера и дала белый экран.

## Что не трогать

- `pkm_v2/**`, `navigation_runtime.js`, `pkm_runtime_v2.js`, `src/core/pkm_*`, `src/core/status_*`, `token_graph_unified.js`, `line_pipeline.js` — кроме смены пути чтения настройки в фазе 2 (З3).
- Значения, которые пишутся в конфиг: переименовываются только подписи (З1).
- Хоткеи по умолчанию не ставятся ни одной команде (З7).
- Контрол, который не работает в текущем релизе, в панели не показывается (З8).

## Известные дефекты, которые выглядят как ошибка окружения

- `tests/regression/status_runtime_behavior_tests.js` красный на чистом чекауте: `vault_module_bridge` не находит модуль по пути `.obsidian/plugins/...`. Внесён в список пропусков `tests/run_all.js` с причиной (A15).
- Линтер находит пять обращений к именам, которых нет в области видимости (`refreshSettings`, `getLineFinalizeUnified`) — вероятно, их подставляет склейка бандла. `no-undef` держится предупреждением до фазы 6 (A14).
- В `main.js` есть встроенная копия `ConfigStore` (`FallbackConfigStore`) помимо модуля. Правки нужны в модуле; в бандле работает он.

## Общение

Документ и комментарии в коде — по-русски, все строки интерфейса — по-английски. Заказчик просит заканчивать ответ **одним конкретным следующим шагом**, а не списком вариантов.
